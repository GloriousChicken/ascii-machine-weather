# The Weather Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give the sea weather that happens on its own — squalls, gusts, fog, clearing, rain and hail — on a repeating cycle, while leaving the weather-free sea byte-for-byte identical to the sea of `ascii-machine-web`.

**Architecture:** A new `src/weather.ts` owns a list of regions (discs on the canonical grid) and a seeded cycle. Each step it writes three things into the simulation — a wind field, a flow scale and an energy mark — plus a canonical wash field and a list of falling drops. The simulation gains the wind field and the flow scale and nothing else; it stays ignorant of the weather. The display side applies the wash to the normalised density before the glyphs are chosen, and the drops are drawn on the 2D overlay canvas.

**Tech Stack:** TypeScript, Vite, WebGL 2, vitest, Playwright. **No new dependencies.**

**Spec:** `docs/superpowers/specs/2026-10-22-weather-design.md` — the plan argues from the spec, so the spec travels with it; executors read both.

## Global Constraints

- The canonical grid is 160x60 and never changes.
- The renderer stays one instanced draw call. The weather adds no draw call; the drops go on the 2D overlay canvas.
- The frame budget is 16.7ms. The frame costs 1.88ms today.
- The simulation advances on a fixed clock at 60 steps per second. One simulation step is one weather step.
- The weather is **not** a user-facing dial and **not** in the URL. The only weather URL parameter is `?weather=off`.
- `?seed=N` gives the same sea and the same weather schedule, at any window size. The cycle's *phase* is not carried by a link, and that is deliberate.
- `?weather=off` gives a sea byte-for-byte identical to `ascii-machine-web`'s, accent levels included.
- The mouse's velocity kick stays dead. `Simulation.stir()` still only persists density and energy.
- Scalar fields are resampled; discrete marks are projected.
- Commits are authored as `GloriousChicken <218804855+GloriousChicken@users.noreply.github.com>`. The repository's local git identity already sets this. No personal names, no email addresses, no local filesystem paths in the tree or the history.
- Commit messages are imperative sentences, no conventional-commit prefixes, matching the existing history.

## Review Focus

The five conditions most likely to bite somebody using this, each of which a task's tests must pin.

1. **A region whose centre drifts off the edge of the grid.** It must reappear on the other side, or storms vanish at the border and the cycle looks broken.
2. **A region whose centre lands exactly on a cell.** The tangential push is derived from the direction away from the centre, so the distance must be guarded against zero.
3. **Two regions overlapping.** The wind fields and the energy marks must add, not overwrite, and the wash must not cancel itself out.
4. **A window resize during a storm.** The wash is a field and resamples; the drops are display-space and must be recomputed at the new size rather than left at the old one.
5. **The weather turned off.** The sea must be identical to `ascii-machine-web`'s, and the accent levels with it — the sea at rest has no accent colour in it, so the clicked fixture is what catches a change there.

### Task 2: The regions and the kinds

**Files:**
- Create: `src/weather.ts`
- Test: `tests/weather.test.ts`

**Interfaces:**
- Consumes: `Simulation` from `src/simulation.ts` — specifically `windVx`, `windVy`, `flowScale`, `energy`, `width`, `height`, and `stir`-style writes to `energy`.
- Produces:
  - `export type WeatherKind = "squall" | "gust" | "fog" | "clearing" | "rain" | "hail";`
  - `export type CycleAct = "calm" | "building" | "storm" | "clearing";`
  - `export interface WeatherRegion { readonly kind: WeatherKind; readonly x: number; readonly y: number; readonly radius: number; readonly driftX: number; readonly driftY: number; readonly spin: number; readonly age: number; readonly life: number; readonly seed: number; }`
  - `export interface KindSpec { readonly radius: number; readonly drift: number; readonly spin: number; readonly push: number; readonly damp: number; readonly heat: number; readonly wash: number; readonly drops: readonly string[]; readonly fallRate: number; readonly impacts: boolean; }`
  - `export const WEATHER_KINDS: Record<WeatherKind, KindSpec>;`
  - `export function weatherKindNames(): WeatherKind[];` — the summon order: squall, gust, fog, clearing, rain, hail.
  - `export class WeatherSystem` with the constructor `(seed: number, options?: { enabled?: boolean })`, the readonly fields `enabled`, `regions`, and the methods `step()`, `applyToSimulation(sim: Simulation)`, `summon(kind: WeatherKind, x?: number, y?: number)`, and `reset()`.
  - `summon` places the region at `(x, y)` in canonical cells, or at the middle of the sea when they are not given. The position is optional so that the `w` key can put a storm under the pointer, and so that the tests can put one somewhere known.

**The kind table, exactly as the spec gives it:**

| Kind | radius | drift | spin | push | damp | heat | wash | drops | fallRate | impacts |
|---|---|---|---|---|---|---|---|---|---|---|
| `squall` | 18 | 0.9 | 0.12 | 0.4 | 0 | 2.0 | 0 | `[]` | 0 | false |
| `gust` | 28 | 1.6 | 0 | 2.0 | 0 | 2.0 | 0 | `[]` | 0 | false |
| `fog` | 36 | 0.35 | 0 | 0 | 0.85 | 0 | 1 | `[]` | 0 | false |
| `clearing` | 32 | 0.25 | 0 | 0 | 0 | 0 | -1 | `[]` | 0 | false |
| `rain` | 22 | 0.6 | 0 | 0.8 | 0 | 0.8 | 0 | `["\\|", "/", "."]` | 0.9 | false |
| `hail` | 24 | 0.5 | 0 | 0 | 0 | 1.2 | 0 | `[".", ",", "'"]` | 2.5 | true |

`heat` is the energy a mark is worth, so `squall` writes 2.0 at its core and `rain` writes 0.8. `damp` is how much of the flow is removed, so `fog` leaves 15% of it. `wash` is signed: positive washes the density towards the middle of the ramp, negative pushes it away.

**The life curve**, used by every region:

```
intensity(t) = smoothstep(0, 0.15, t) * (1 - smoothstep(0.65, 1, t))
```

where `t = age / life`. `smoothstep(edge0, edge1, x)` is `x` clamped to `[0, 1]`, then squared times `3 - 2x`.

A region therefore builds over the first fifteenth of its life, which for a
squall is about 225 steps, or nearly four seconds. That is deliberate: a
storm that is already at full strength the instant it appears is a shape,
not weather. A summoned storm takes a few seconds to gather, and the tests
step past the build before they measure anything.

**The push**, for a cell at distance `d` from a region's centre:

```
falloff = exp(-(d * d) / (radius * radius))
push    = falloff * intensity
tangential = spin * d          // only when d > 0
```

The tangential direction is perpendicular to the radius: `(-dy / d, dx / d)`. The directional push is along `(driftX, driftY)` normalised. The region's centre advances by `(driftX, driftY)` each step, wrapping toroidally over the canonical grid.

import { Simulation } from "../src/simulation";
import { WEATHER_KINDS, WeatherSystem, weatherKindNames } from "../src/weather";

/**
 * Steps the weather until a region is at full strength.
 *

function settle(weather: WeatherSystem, steps = 300) {
  for (let i = 0; i < steps; i++) weather.step();

| Act | Steps | What happens |

- [ ] **Step 3: Implement the cycle**

Add to `WeatherSystem`: a `stepCount`, a readonly `act`, and the table of act lengths above. `step()` increments the step count, and when the act's length is reached, moves to the next act and spawns that act's regions.

- [ ] **Step 3: Implement the wash and the drops**

**The wash** is a canonical-sized array on the system, rewritten every step: zeroed, then for every region with a non-zero `wash` value, `wash[index] += falloff * intensity * spec.wash`, clamped to `[-1, 1]`. Overlapping regions add, and the clamp keeps the result in range.

**The drops** are computed per kind that has any. For a region with drops, walk the canonical columns across the region's width, and for each one decide from the region's seed and the step count whether there is a drop, and where it is. The drop's canonical row is derived from its phase and the region's `fallRate`, and the canonical position is then projected into display cells by `columns / 160` and `rows / 60`. The glyph comes from the kind's `drops` list, chosen by the same hash.

The hash must be a pure function of the region's seed, the column and the step count, so the drops are reproducible and change as time goes on.
